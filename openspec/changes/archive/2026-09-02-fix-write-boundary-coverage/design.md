## Context

`harden-bridge-transport` 修好了一条 CRITICAL (未 flush 的请求永久挂起), 但它的姊妹路径 —— "write 回调晚于 `close()` 到达时必须判 `SENT_LINK_LOST`" —— 在仓库内的测试是空转的.  这条路径的实现正确性已由两个独立来源确认 (reviewer 的代码审读, tester 用真实背压的一次性验收), 缺的只是**持续保护**.

发现过程本身值得记录: reviewer 是在给主 agent 复现"同步 throw 路径"时撞上这个机制的, 它自己的第一版探针也被抹掉并得出假结果, 差点把正确实现误报成 bug.  也就是说, 这个陷阱既能让测试假绿, 也能让排查假红.

## Goals / Non-Goals

**Goals:**
- 让那条安全关键边界在仓库内获得真实、可持续的测试保护
- 建立一条规矩, 使同类静默失效在将来能被立即发现而不是靠偶然撞见
- 收掉三项诊断质量遗留与一项工程卫生遗留

**Non-Goals:**
- 不拆分 `src/bridge-client.ts` (下一轮; 顺序不可颠倒, 理由见 Decisions 第 1 条)
- 不改变任何对外协议语义与错误码含义
- 不与真实 bridge / 真实 Chrome 联调

## Decisions

**1. 本轮只补覆盖不做重构, 顺序不能颠倒**

`bridge-client.ts` 现有 539 行确实偏大, 但本项目至今出现的所有真实缺陷都落在**生命周期状态之间的交互**上 (写时序 × close × 计时器), 而唯一守着这条交互的测试正是空转的那条.  在这个状态下做"等价变换", 没有可靠测试背书, 风险高于继续放着.  先补覆盖, 再重构, 那时"测试全绿背书"才名副其实.

**2. 用真实内核背压制造延迟, 而不是修好打桩方式**

绕开 Node 的抹除有两条路: 把包装器装进 `socket.once("connect", ...)` (抹除发生在 `connect()` 同步阶段, 早于 connect 事件), 或者干脆不打桩, 用对端 `pause()` + 大帧制造真实的 `write` 返回 false.

选后者.  理由: 打桩验证的是"我假设的时序", 真实背压验证的是"内核真的会这样".  这条路径的全部风险恰恰在于对 `write` 回调时机的假设是否成立 —— 用假设去验证假设没有意义.  tester 的验收脚本已经证明这条路可行且稳定 (`socket.write` 返回 false, close 前回调次数为 0), 直接照搬其手法即可.

**3. "桩必须自证生效"作为一条规矩落到测试里**

真正的教训不是"这条测试写错了", 而是"一个失效的桩看起来和一个生效的桩完全一样".  因此凡是保留打桩的测试, 都要断言桩确实被调用过.  这条断言的成本是一行, 而它把一类静默失效变成了显式失败.

注意边界: Node 只还原 `write`, 不还原 `connect` —— 覆盖 `connect` 的桩 (握手计时器那条测试用的) 是有效的, 不要连坐.

**4. 诊断降噪按"帧类型先选分支"而非"事后过滤"**

两种实现都能去掉噪音: 按 `type` 字面量先选中分支再展开, 或展开后丢弃 `path[0]` 在原始帧中不存在的 issue.  前者更可取 —— 它表达的是"这个帧本来就该按哪个分支校验", 而后者是在结果上打补丁, 遇到分支间字段重名时仍会漏.

降噪不得牺牲定位能力: 上一轮刚把可诊断性从 `invalid_union / "Invalid input" / path:[]` 提升到带真实 path 的具体错误, 这是本项目跨仓库排查的主要抓手, 不能在降噪时又丢回去.

**5. 超长行提取 id 用有界前缀正则, 不解析整行**

reviewer 指出的假二选一: 超限的完整行早已整行驻留内存 (它是从缓冲切出来的), 资源代价已经付过; 真正值得省的是 `JSON.parse` 的对象图分配.  在行首有界前缀 (量级为百字节) 上跑一个有界正则, 既能拿到 `id`, 又不构造对象图, 两个目标同时满足.

提取失败时按原路丢弃 —— 不做任何兜底猜测, 因为归属错请求比不归属更糟.

## Risks / Trade-offs

- **2MiB 帧的测试会增加单测耗时与内存占用** → 相对于它保护的路径 (判错即重复点击) 这是划算的; 若耗时明显, 可下调到刚好超过发送缓冲的量级, 但必须保证 `write` 确实返回 false 并断言之
- **真实背压依赖操作系统的 socket 缓冲行为** → 不同平台缓冲大小不同, 因此测试断言的是"`write` 返回 false 且回调未触发"这个可观察事实, 而不是某个具体字节数
- **降噪可能误伤定位信息** → 以"降噪后仍能指出具体字段路径"作为验收条件之一, 而非只检查噪音消失
- **有界正则提取 id 可能被构造出的畸形前缀骗到** → 提取到的 id 必须在等待表中命中才结算, 命中不了就丢弃; 不存在"猜一个最近的请求"这类兜底

## Open Questions

- 诊断展开的深度上限与条数上限的具体取值, 由实现给出并在 review 阶段确认合理性
- 有界前缀的长度取值同上 (需覆盖典型帧中 `id` 出现的位置, 又不能大到失去意义)
