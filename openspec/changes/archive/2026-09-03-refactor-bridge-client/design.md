## Context

`src/bridge-client.ts` 560 行 / 36 方法.  基线是 commit `73cf4d5` —— 三个 change 已归档提交, 工作区干净, 89 个测试全绿, 因此本轮的等价性可以直接用 `git diff 73cf4d5` 审阅.

拆分的时机不是任意选的.  reviewer 在两轮 review 里都建议拆, 但都附了同一个前置条件: **先建立真实的测试覆盖**.  它的论证是: 本项目全部真实缺陷都落在生命周期状态之间的交互上, 而当时唯一守着这条交互的测试是空转的 (Node 的 `net.Socket.prototype.connect` 会还原打在 `socket.write` 上的桩), 在那种状态下做等价变换, "测试全绿背书"是空话.  该前置条件已在 `fix-write-boundary-coverage` 中满足并经独立 e2e 复现.

## Goals / Non-Goals

**Goals:**
- 把两条生命周期从同一个类里分开, 使它们的边界成为代码结构而不是阅读者的记忆
- 保持全部可观察行为**逐字节不变**
- 补上联调前的两项准备 (交叉校验、快照补强), 两者都不触碰实现

**Non-Goals:**
- 不修任何 bug, 不调整任何错误码或提示文案, 不改变计时器起表时机
- 不动 `src/framing.ts` (155 行, 内聚良好)
- 不做 `extractOversizedResponseId` 的深度扫描 (行为变化, 单独一轮)
- 不做与真实 bridge / 真实 Chrome 的联调 (下一轮)

## Decisions

**1. 拆分边界: 连接生命周期 vs 请求生命周期**

连接侧: connect、握手与握手超时、关闭、两类计时器的持有.
请求侧: pending 表、write 与写出确认标记、结算、按 id 归属.

这条边界不是按"代码行数均分"选的, 而是按**故障归属**选的: 历史上每一个真实缺陷都可以干净地归到其中一侧 (握手活锁 → 连接侧; 假 `NOT_SENT` → 请求侧; 兜底计时器永不起表 → 两侧交界).  按这条线拆开之后, 交界处需要的协作会变成显式的接口调用, 而不是同一个 `this` 上的隐式共享状态.

**2. 三处历史耦合必须保持成对, 且拆分后应更难拆散**

这三对是本项目付出过代价才建立起来的, 拆分时任何一半掉队都会重新制造已知缺陷:

- **握手超时 × 兜底计时起点后移**: 缺前者则"连接成功但永不 hello"的请求没有任何计时器; 缺后者则握手耗时挤占请求预算.  两者一起才既不过早也不永不超时
- **关停路径 × `writeMayHaveBeenSent` 同步置位**: 缺后者则关停时已写出的请求会被报成 `NOT_SENT` (可安全重试), 而真实后果是重复点击/重复提交
- **未知字段 passthrough × 保留键互斥强校验**: 缺后者则畸形 error 帧会命中成功分支, MCP 响应丢掉 `code` 字段

拆分后这三对分别落在何处, 要在实现中显式体现 (例如同一模块内相邻、或接口签名上强制同时提供), 而不是散在两个文件里靠约定维系.

**3. 等价性的唯一背书是既有测试, 因此不得修改既有断言**

现有 89 个测试是这次拆分能否被信任的全部依据.  允许调整的只有 import 路径; **任何断言的修改都会使等价性论证失效** —— 如果拆分需要改断言, 那说明行为变了, 应当停下来而不是改断言迁就.

这条比通常的重构纪律更严, 原因是本项目已经出现过两次"修 A 引入 B": 严格 schema 改 passthrough 打穿了 error 载荷校验; 兜底计时器移进 write 回调制造了永久挂起.  两次都是在"看起来更好"的改动中引入的.

**4. 交叉校验只断言判定结论, 不断言 schema 结构相等**

两侧 schema 的写法不同 (本侧是三轮打磨的实现, 对端是共享包声明), 结构相等既不成立也无必要.  有意义的是**行为等价**: 对同一个样本, 两者接受或拒绝的结论一致.

对端已澄清三类帧的性质不同, 这决定了交叉校验的价值分布: `tool_request` 与 `hello` 对端**真的在用**那份 schema; 而 `tool_response` 那份是**规范性声明而非对端运行时闸** (bridge 的出帧是从 extension 帧的 strict 解析结果重建的).  因此交叉校验对 `tool_response` 价值最大 —— 它测的正是"对端声明 vs 本侧接受行为"这条否则无人守护的边.

**5. 预期差异必须显式排除, 不能靠断言恰好没覆盖到**

对端在 `hello` 的 `protocol_version` 用字面量约束 (版本闸语义, 故意的), `bridge_version` / `tool_defs_version` 带 semver 格式约束.  这些位置对端"声明从严"、本侧"接受从宽", 是有意为之而非漂移.

处理方式必须是**显式声明排除**, 而不是让样本集恰好绕开它们.  区别在于: 显式排除会在对端某天收紧或放宽这些位置时仍然可见; 而"恰好没测到"是隐形的, 且会随样本集的任何一次扩充意外变成红灯或漏网.

## Risks / Trade-offs

- **拆分引入行为变化而测试没抓到** → 这是本轮的核心风险.  缓解: 既有断言一字不改; e2e 做既有场景的全量回归; `git diff 73cf4d5` 可供逐处审阅.  但必须承认测试覆盖不是全集, 因此**任何"顺手改进"都被禁止** —— 不是因为改进不好, 而是因为它会污染这次等价性判断
- **拆出来的模块边界选错, 下次改动反而更难** → 缓解: 边界按故障归属而非行数选取; 若实现中发现某处协作过于频繁以致接口臃肿, 这本身是边界选错的信号, 应当报告而不是硬拆
- **交叉校验把预期差异误判成漂移, 制造噪音** → 缓解: 预期差异显式声明并注明理由; 一旦对端改动这些位置, 显式声明的那行代码就是需要更新的地方, 有迹可循
- **对端共享包仍可能演进** → 对端已完成 harden 并 commit, 当前是稳定态; 但 `file:` 依赖仍无版本锚定, 交叉校验与快照都会在对端变动时立刻响 —— 这是设计意图, 不是缺陷
