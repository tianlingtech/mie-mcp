## 5. 与共享包的交叉校验

- [x] 5.1 建立帧样本集, 至少覆盖既有实测矩阵的全部形态: 接受侧 (hello 带未知字段 / 成功响应带未知字段 / 错误响应带未知字段 / `error.data` 带未知字段) 与拒绝侧 (`error` 为 `{}` / 字符串 / null / true / `[]` / `code` 为数字 / `code` 为空串 / 两个保留键同时存在 / 同时缺失 / `id` 缺失 / `id` 为空串)
- [x] 5.2 每个样本分别经本仓库校验与 `@mie/tool-defs` 的 `./socket-protocol` 校验, 断言按**帧方向**分成两种, 不得混为一条"结论一致":
  - **入站帧** (`tool_response` / `hello` / `event`): 断言"对端接受的本侧必接受" (对端声明是本侧的子集).  本侧更宽容不算失败
  - **出站帧** (`tool_request`): 断言"本侧接受的对端必接受" (本侧是对端的子集).  本侧更宽容**是失败** —— 对端那份是运行时闸而非声明, 违反它的帧会被直接拒绝, 本侧宽容意味着发送侧护栏失效
- [x] 5.3 只断言判定结论, **不断言 schema 结构相等** (两侧写法本就不同, 结构相等既不成立也无必要)
- [x] 5.4 预期差异**显式声明并注明理由**, 不得靠样本集恰好绕开.  三处 (均为对端声明从严、本侧接受从宽, 有意为之): (i) `hello` 的 `protocol_version` 字面量约束 (版本闸语义); (ii) `hello` 的 `bridge_version` / `tool_defs_version` semver 格式约束; (iii) **`tool_response` 的 `payload` 形态** —— 对端要求对象, 本侧接受 primitive (`null` / `0` / `false`)
- [x] 5.4b `payload` primitive 这条差异必须以"预期差异"形式**进入样本集并被断言为已知不一致**, 而不是把样本从集合里删掉 —— 前者在对端某天放宽时会亮起来, 后者是隐形的
- [x] 5.4c 本侧对 primitive payload 的宽容接受是既有且有测试守护的行为, **不得为消除该差异而收紧**; 对端契约理由 (payload 内加键才能无痛增量演进, 裸标量需包一层 `{value: ...}`) 记入注释
- [x] 5.4d 入站侧第四条预期差异: `tool_response` 的 `error.message` (对端要求非空, 本侧 optional 且接受空串并有 fallback).  注释中 MUST 写明"对端保证非空, 且该字段承载建议动作 (如 `SENT_LINK_LOST` 必须提示先截图确认副作用), 本侧 fallback 仅为防御" —— 免得日后有人据此认为 message 可有可无
- [x] 5.4e **出站侧 (`tool_request`) 的差异单独归类, 不进"预期差异"清单**.  已枚举出三条: `timeout_ms` 缺失 (本侧必填/对端 optional 缺省 30000)、顶层未知字段 (本侧 strict/对端 loose)、`args` 形态 (本侧接受 primitive/对端要求 record 且必填).  前两条本侧更严, 是正确方向, 记录即可; **第三条本侧更宽, 是发送侧护栏失效**, 属缺陷
- [x] 5.4f `args` 那条 (本侧接受 primitive) **本轮不修** —— 收紧是行为变化, 违反本轮铁律.  记入 change 的收尾报告作为后续项, 并在交叉校验测试里以"已知缺陷"形式标注 (而非静默排除), 使它在被修复后能立刻反映出来
- [x] 5.5 验证这组断言确实能发现分歧: 临时改动本侧或样本使两边结论不一致, 确认测试失败, 再还原
- [x] 5.6 `tool_response` 一类的样本覆盖最完整 —— 对端那份是规范性声明而非其运行时闸, 这条边否则无人守护
- [x] 5.7 对端已给出"清单完结声明": 除已知的 8 条外 `socket-protocol` 不存在其他收窄.  若本轮枚举跑出清单之外的差异, 那是**真发现**, 立即报告主 agent 而非自行归类
