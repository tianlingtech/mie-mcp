## Context

`add-bridge-transport` 已交付并通过 3 轮 verify、1 轮 review (PASS_WITH_WARNINGS) 与 11 项独立 e2e, 但留下 5 条未修 WARNING.  同时 mie 仓库的 `packages/tool-defs` 已定稿并锁定 zod v4, 而本仓库是 zod 3.25.76 + `zod-to-json-schema`.

两件事必须一起做: v4 里 `z.unknown()` 的可选语义与 v3 不同, 而当前 `src/protocol.ts` 的 payload/error 互斥校验正是建立在 v3 那个语义之上 —— 上一轮 verify 的 W5 明确记录了这一点 (v3 里 `payload: z.unknown()` 本身可选, 导致 error 帧误命中 Success 分支).  W4 的按 id 结算也落在同一条校验路径上.

已确认的边界: 与 mie-main 核对后, `packages/tool-defs` 的 `./protocol` 是 extension↔bridge 的 native messaging 内层协议 (strict + 封闭错误码枚举在内层是有意的, bridge 对外发帧是从 strict 解析结果重建的), 与 socket 层无关.  **socket 层语义零变化**, 本 change 不改变任何对外协议语义, 不需要提升 `protocol_version`.

## Goals / Non-Goals

**Goals:**
- 迁到 zod v4 且两侧矩阵 (未知字段前向兼容 / 畸形 error 拒绝) 同时为绿
- 消除两条会在联调期误导排查方向的缺陷: 握手活锁、校验失败帧熬到超时
- 让长驻进程该退能退、该活着的时候不被单个 handler 异常掀翻
- 错误码语义在"是否已发出"这个维度上准确

- 接上 `@mie/tool-defs`, 注册 6 个 P0 tool, 使本侧达到"只差把对端从 fake bridge 换成真实 bridge"的状态

**Non-Goals:**
- 不与真实 bridge / 真实 Chrome 联调 (另起一轮)
- 不改变 socket 层对外协议语义, 不提升 `protocol_version`
- 不新增错误码

## Decisions

**1. zod v4 迁移用内置 `z.toJSONSchema`, 移除 `zod-to-json-schema`**

v4 自带 JSON Schema 导出, 保留第三方转换器等于维护两套语义.  迁移的风险不在依赖替换, 而在 `src/protocol.ts`: 必须重新确认"未知字段 passthrough"与"保留键互斥 + 错误载荷强校验"在 v4 语义下**同时**成立.  这两条曾经在上一轮里此消彼长过一次 (放宽 schema 修好前向兼容, 却让 error 分支校验失效), 所以迁移的验收标准是两侧矩阵同时为绿, 而不是"测试通过".

**2. 握手超时到点 destroy socket, 而不是只 reject 握手 promise**

活锁的根因是握手 promise 永不 settle 时 socket 也永不 close, 于是连接关闭回调不触发, 客户端状态永远停在"已连接未握手".  只 reject promise 不能解除这个状态.  destroy socket 会触发既有的连接关闭路径, 让重连逻辑自然接管 —— 复用现成路径而不是新增一条恢复分支.

握手超时是独立于请求超时的第二个计时器: 请求超时的归属方是 bridge (它计时并回 TIMEOUT 帧), 而握手阶段还没有请求可归属, 只能由本侧兜底.

**3. 兜底计时从写出确认起算, 且不因此放弃"永不挂起"**

计时起点后移解决的是"握手耗时挤占请求预算".  但它带来一个副作用: 若连接建立后永远没有写出确认, 请求就没有任何计时器 —— 这正是上一轮 S1 被拒绝的理由 (拒绝理由当时判定成立).  决策 2 的握手超时恰好补上了这个缺口: 写不出去的唯一现实原因是握手未完成, 而握手现在有独立超时.  两条必须一起落地, 单独做任何一条都会留下一个挂起路径.

**4. 校验失败帧按 id 结算时用 `TOOL_ERROR` 而非新码**

这条失败发生在"bridge 已经响应"之后, 属于对端行为异常, 不是本地未发出, 因此 `NOT_SENT` 不合适; 而 `TIMEOUT` 正是要避免的错误归因.  在不新造码的约束下, `TOOL_ERROR` 是唯一语义可接受的选择, 真正的信息量由错误消息里的校验详情承载.

**5. 未发出的本地失败改用 `NOT_SENT`, 但不为版本不兼容新造码**

上一轮 verifier 判定"不在单仓单侧新增跨协议错误码"的理由成立, 本 change 继续遵守.  版本不兼容确实"未发出", 用 `NOT_SENT` 在这个维度上是准确的; 它附带的"可安全重试"含义在此处无害 —— 重试会立即再次失败且不产生任何副作用, 而错误消息里保留的双方版本号足以让 agent 判断不必重试.

**6. 诊断脱敏采取"只记长度或前缀哈希"**

mie 的载荷是登录态下的页面数据, 诊断默认写 stderr.  被丢弃的畸形帧恰恰是最可能包含意外内容的那一类.  代价是排查时看不到原文 —— 用长度与哈希足以判断"是不是同一个帧反复出现", 而需要看原文的场景应当在对端排查, 不应以本侧日志留存敏感数据为代价.

**7. 关停路径与写出确认时序必须同批落地**

上一轮 S2 记录了一个当时不可达的隐患: 写已 flush 但确认回调尚未执行的同步窗口内若发生关停, 会得到假 `NOT_SENT`.  它当时不可达的前提正是"没有同步关停路径", 而本 change 要加的就是关停路径.  因此这两条是同一件事的两半, 分开做会亲手制造一个"报可安全重试、实则可能已执行"的路径 —— 那是这套错误码里后果最重的方向 (重复点击/重复提交).

**8. 只取共享包的 `./schemas` 与常量, 协议校验留在本仓库**

与 mie-main 核实的结论: 共享包的 `./protocol` 是 extension↔bridge 的 native messaging 内层协议.  它的 strict 与封闭错误码枚举在内层是有意的 —— extension 与 bridge 同仓同版本发布, 且 bridge 对外发帧是从 strict 解析结果**重建**的, 这正是"成功帧绝不带 error 键"这条保证的来源.  但同样两条特性放到 socket 层就是有害的: strict 会让对端加一个可选字段就打穿前向兼容, 封闭枚举会让未知错误码被拒而非透传 —— 这两条恰是本仓库前一轮 verify 花两轮修出来的保证.

因此取舍是: **参数结构的单一来源在共享包** (tool 输入定义, 语义由 extension 的实现决定, 本仓库只是下游), **socket 帧校验的单一来源在本仓库** (它表达的是跨仓库前向兼容策略, 而策略的承受方是本侧).  `ERROR_CODES` 取其值作提示参考表, 不取其 schema 作校验闸.

代价是"协议"这个词在两个仓库各有一份定义.  这不是重复, 而是两层不同的协议; mie-main 已把"tool-defs 显式区分 native 层与 socket 层入口"记入其 backlog, 届时可重新评估是否切换.

**9. `file:` 依赖是开发期方案, 不是最终形态**

共享包尚未发布, 当前以 `file:` 指向 mie 仓库工作区.  这意味着构建结果依赖本机的目录布局, 且对端代码尚未提交 —— 换一台机器或 CI 都跑不起来.  本 change 接受这个限制 (jt 的指示是先把本侧做完, 发布方式后议), 但实现上要把这层依赖收敛在一处适配层内, 使日后换成版本化依赖时改动面最小.

**10. `computer` 的 union 输入需要确认 MCP 客户端可用性**

`computer` 的输入是按 `action` 判别的 union, 派生 JSON Schema 后会是 `anyOf`.  这在 MCP 规范内合法, 但不同客户端对 `anyOf` 的呈现与校验支持不一.  实现时必须实际确认派生结果可用, 而不是只看类型通过 —— 这是 6 个 tool 里唯一一个结构上有风险的.

## Risks / Trade-offs

- **zod v4 的 schema 结构与 v3 有差异, 派生出的 MCP tool schema 可能变形** → 迁移后需确认工具列表中的 input schema 与 zod 定义仍然等价; 这条有现成用例覆盖, 但 v4 的输出结构变化需要人工确认一次
- **握手超时阈值取值** → 取太短会在慢机器上误杀正常握手, 取太长则活锁的暴露被推迟.  倾向取一个明显小于请求兜底 (35s) 但足够宽松的值, 并使其可配置以便测试注入
- **缓冲上限阈值** → 必须高于最大截图 base64 单帧, 否则会误杀正常的大响应; 这个上限的正确性依赖对未来 tool 载荷规模的估计, 属于本 change 内唯一带预估成分的取值
- **本 change 不改对外语义, 但改了大量内部路径** → 回归风险集中在 `src/bridge-client.ts`; 现有 37 个用例是主要护栏, e2e 必须覆盖新增的三条路径 (关停、握手超时、按 id 结算)
- **`file:` 依赖指向的对端代码未提交** → 对端工作区若发生变动, 本侧构建结果会随之改变而无版本可锚定; 缓解方式是把适配层收敛在一处, 并在联调轮之前不假设该包稳定
- **引入共享包可能反向收窄本侧保证** → `ERROR_CODES` 若被误用作校验闸, 会静默撤销未知码透传; spec 已就此写成显式 requirement, 并要求 e2e 用一个不在枚举内的错误码验证
