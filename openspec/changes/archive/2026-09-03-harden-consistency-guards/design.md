## Context

上一轮 (`refactor-bridge-client`) 的 review 留下五条 SUGGESTION, 其中三条被判定为"值得在联调前做掉".  它们的共同性质是: **不是当前的缺陷, 而是让已经踩过的坑能够再次发生的形状**.

本项目已经在同一类问题上付出过两次代价: 一条因 Node 还原 `socket.write` 桩而空转的测试 (看起来覆盖了最危险的边界, 实际一次都没跑过); 一条因 spec 从未表达某个不变式而在 spec 层面"合规"的行为回退 (兜底计时器被移进 write 回调, verify 判不出问题, 一路走到 review 才被抓).  这三条改动分别对应这两类教训.

## Goals / Non-Goals

**Goals:**
- 让"可空转的条件断言"这个形状在本仓库不再可复用
- 让交叉校验的两条方向不变式在代码里可读, 而不是只存在于表结构的隐含语义中
- 把关闭路径的同步性约束从"注释能提醒的"提升为"requirement 能拦住的"

**Non-Goals:**
- 不改变任何实现语句 (第三条只加注释)
- 不改动任何既有测试断言
- 不收紧 `tool_request.args` (行为变化, 已用 `it.fails` 登记, 单独一轮)
- 不与真实 bridge / 真实 Chrome 联调

## Decisions

**1. 消除形状, 而不是给形状加防护**

`assertOutboundDirection` 有两种修法: 内联进 `it.fails` 块 (形状消失), 或保留 helper 但强制 `expect.hasAssertions()`.

倾向前者.  理由: 后者是"给危险形状加一道护栏", 而护栏依赖后来者记得触发它; 前者是"让危险形状不存在".  本项目在空转测试那次的教训正是——**一个失效的护栏看起来和一个生效的护栏完全一样**.  但若 coder 判断内联会显著损害可读性, 后者可接受, 前提是护栏本身有测试证明会触发.

无论选哪种, 验收条件相同: **构造一个"本侧拒绝"的样本走该路径, 证明它不会零断言通过**.

**2. 方向不变式写成陈述式意图注释, 不是解释代码**

项目规范禁止解释性注释.  这里要写的不是"这段代码在做什么", 而是"**这个文件强制的两条不变式是什么**" —— 入站"远端接受则本侧必接受", 出站"本侧接受则远端必接受".  四张表是这两条规则的样本编码, 而规则本身在代码里无处可读, 只能从表名和断言元组反推.  加样本的人若反推错方向, 会得到一个全绿但断言错了方向的测试, 而方向搞反正是这层防护唯一的失效方式.

**3. 关闭路径的约束同时进注释与 spec, 两者作用不同**

注释拦的是改代码的人 (读到它就会知道不能把 `onClosed` 改成 async); requirement 拦的是 verify (没有 requirement 就判不出违反).

上一轮的教训明确指向后者: 当时 verifier 判不出兜底计时器的回退, 不是它失职, 是**spec 里根本没有那条不变式**, 它按 spec 判当然判不出.  只加注释会重演这个局面 —— 注释不是判定依据.

**4. 本轮实现语句一行不改**

第三条只加注释.  这不是保守, 是因为当前实现**已经满足**该约束 (上一轮的行为差分与 review 都确认过等价).  requirement 的作用是防止未来破坏, 不是修复现在.

## Risks / Trade-offs

- **内联 `assertOutboundDirection` 可能造成重复代码** → 若重复到影响可读性, 改用 `expect.hasAssertions()` 方案, 但那时护栏自身需要证明会触发
- **新增 requirement 描述的是"既有约束"而非新行为, 可能被误读为本轮实现了什么** → proposal 与 design 均已写明实现语句未改; 该 requirement 的价值在于未来的 verify 能据此判定
- **"同步完成"这个措辞需要精确** → 约束的实质是"清理不跨异步边界", 而非"必须在某个特定函数内" —— 措辞按前者写, 避免把当前的实现结构写死进 requirement, 重蹈此前三次措辞脱节的覆辙
