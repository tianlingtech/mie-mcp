## Context

诊断脱敏是几轮前作为隐私改进加的, 理由至今成立.  但 reviewer 在联调前提出: **同一个性质在联调场景下反转成了排查成本** —— 对端回帧不对时手上只有长度和哈希, 而那正是最需要看内容的时刻.

这不是"当初做错了", 而是同一个默认值在两种场景下代价不同.  本轮的判断是: 默认不动, 留一个显式出口, 并且**现在**就留好 —— 而不是等联调半夜卡住时临时加一个没人审过的调试分支.

## Goals / Non-Goals

**Goals:**
- 联调时能看到对端发来的具体帧内容
- 默认路径的隐私性质**一字不变**
- 把解码回调的同步性不变式补进 spec (上一轮 review 留下的账)

**Non-Goals:**
- 不放宽默认值
- 不改变任何协议语义、错误码、提示文案、计时器时机
- 不收紧 `tool_request.args` (联调后单独一轮)
- 不做联调本身

## Decisions

**1. 选项字段是真实来源, 环境变量只是入口的读取方式**

两层而非一层: `BridgeClientOptions` 上的显式字段是库层的真实来源 (可被测试直接驱动, 不依赖进程环境); 入口从环境变量读取并传入.

只做环境变量会让测试被迫操纵 `process.env` —— 那是全局可变状态, 并行测试下互相污染.  只做选项字段则联调时用不上: MCP server 是被 agent host 拉起的子进程, 改它的启动参数不便, 而设一个环境变量容易.

**2. 默认值的守护交给既有测试, 不新写一个**

现有的脱敏测试 (往畸形帧塞可识别标记, 断言标记不出现在诊断中) 就是"默认路径没有被削弱"的保证.  本轮**不修改它的断言** —— 它继续以原样通过, 就是默认行为未变的证据.

新增的测试只覆盖新增的行为 (开启后可见、开启后有界、不会自行开启).

**3. 开启后仍然截断, 因为排查工具不该变成故障源**

一个 72MiB 的超长帧若原样进日志, 会打爆终端或日志系统 —— 而超长帧恰恰是最可能触发详细诊断的场景之一.  截断上限的具体取值由实现给出并在 review 阶段确认; 关键是**截断必须被标注**, 否则看到的人会以为帧就是那么长, 反而误判.

**4. "不得自动开启"写进 requirement, 不只是实现约定**

这条看似多余 (谁会写自动开启?), 但它防的是一类很自然的"改进": 有人为了方便, 加一个"检测到某种环境就自动开启"的逻辑, 或者把上次的选择记下来.  那会让一个默认关闭的隐私开关在无人察觉处变成默认开启.

写进 requirement 而不是只写注释, 依据是上一轮确立的规矩: **注释拦改代码的人, requirement 拦 verify**.

**5. 解码回调的同步性并入现有 requirement, 而不是新起一条**

它与连接关闭回调是同一条不变式的两个实例 (跨模块同步回调, 同步性承重), 分成两条 requirement 会让"这是同一类约束"这个事实丢失.  措辞上约束**性质** (回调不跨异步边界) 而非当前的调用结构 —— 本项目已有三次措辞脱节的教训, 都是把当时的实现结构写死进了 requirement.

requirement 里额外记了一句"也不会被类型检查发现": 返回 promise 的回调在类型上通常仍然合法, 所以这条既躲过差分测试也躲过 typecheck, 只能靠 requirement 显式约束.

## Risks / Trade-offs

- **开关本身成为泄露途径** → 默认关闭 + 禁止自动开启 + 既有脱敏测试不改断言继续通过; 三条一起, 任何一条被破坏都会有测试或 verify 挡住
- **开启后日志过大** → 截断并标注; 上限取值在 review 阶段确认
- **两层配置 (选项 + 环境变量) 增加一处不一致的可能** → 环境变量只在入口读取一次并传入, 不在库层读 `process.env`; 库层永远只认选项字段这一个来源
- **联调时忘了开, 或开了忘了关** → 忘开只是回到默认体验; 忘关的后果是诊断更详细, 而进程重启即恢复默认 (因为禁止持久化) —— 这正是"禁止持久化"的价值之一
