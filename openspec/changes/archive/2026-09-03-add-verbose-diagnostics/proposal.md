## Why

诊断脱敏 (只留 `length` + `prefixHash` + `topLevelKeys`) 在隐私上是对的, 而且理由至今成立: mie 传输的载荷是浏览器登录态下的页面数据, 被丢弃的畸形帧同样可能携带敏感内容, 而诊断默认写往 stderr.

**但同一个性质在与真实 bridge 联调时会反转成排查成本**: 对端回帧不对时, 手上只有一个长度和一段哈希 —— 而那恰恰是最需要看到帧内容的时刻.  联调是跨仓库的, 卡住时的沟通成本比本地调试高一个量级.

这不是"脱敏做错了", 而是**同一个默认值在两种场景下的代价不同**.  正确的解法不是放宽默认, 而是留一个显式的、默认关闭的出口 —— 并且**现在**就留好, 而不是等联调半夜卡住时临时加一个没人审过的调试分支.

顺带补一笔上一轮 review 留下的账: 主 spec 里「连接关闭的状态清理必须同步完成」只覆盖了连接关闭路径, 而同类不变式在解码回调那侧还有一个活实例未被表达.

## What Changes

**opt-in 的详细诊断 (行为变化)**

- `BridgeClientOptions` 新增一个显式字段, **默认关闭** —— 这是库层的真实来源, 可被测试直接驱动
- 入口从一个环境变量读取该值并传入: 联调时 MCP server 是被 agent host 拉起的子进程, 改启动参数不便而设环境变量容易
- 开启时诊断可包含帧原文, 但**仍有长度上限**并在截断处标注 —— 否则一个 72MiB 的超长帧会直接打爆日志, 把排查工具变成新的故障源
- **关闭时的行为必须与当前逐字节一致**: 现有的脱敏测试 (往畸形帧塞可识别标记, 断言标记不出现在诊断中) 必须继续通过且**断言不得修改** —— 它是"默认路径没有被削弱"的唯一保证

**补全回调同步性不变式**

- 解码回调 (`onFrame` / `onOversizedResponse`) 与连接关闭回调是同一类不变式: 跨模块的同步回调, 且同步性承重.  一旦变成异步, socket data 边界的 try/catch 就再也兜不住 (被拒 promise 会逃逸 —— 正是几轮前那条 WARNING 修掉的东西), 且帧的处理顺序会乱
- 纳入 spec 的形式 (给现有 requirement 加兄弟 scenario, 还是把措辞泛化) 由实现判断, 但覆盖必须真实存在

## Capabilities

### New Capabilities
无.

### Modified Capabilities
- `bridge-transport`: 修改「诊断输出不回显帧内容」—— 从无条件禁止改为"默认禁止, 仅在显式开启时可包含且需截断"; 扩展同步回调的不变式覆盖到解码回调

## Impact

- 受影响代码: `src/bridge-client.ts` 或其选项定义 (新增字段)、`src/bridge-diagnostics.ts` (按开关决定输出形态)、`src/index.ts` (读环境变量)、`src/framing.ts` (若解码侧诊断也受开关影响)
- **不改变**: 任何协议语义、错误码、提示文案、计时器时机; 关闭状态下的一切可观察行为
- 基线: commit `0b1f13e` (五个 change 已归档提交, 工作区干净, 124 tests, 主 spec 26 条 requirement)
- 安全约束: 开关的存在**不得**让默认路径泄露任何东西; 开启必须是显式的、每次进程启动重新指定, **不得有任何形式的持久化或自动开启** (包括但不限于写配置文件、记住上次的值、根据环境推断)
- 不在本次范围: 收紧 `tool_request.args` 为 record (已用 `it.fails` 登记的已知缺陷, 且经确认在联调链路上打不到 —— `ToolRegistry` 传给 bridge 的永远是 zod object schema 产出的 record, 只有直接调用底层 client 才构造得出); 与真实 bridge / 真实 Chrome 的联调本身 (下一轮)
